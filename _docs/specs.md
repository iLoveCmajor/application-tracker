# Application Tracker — spec

14 Nov 2026 · @Vladimir

## Overview

Application Tracker is a single-user web app for tracking job applications through stages. It keeps
each application's history, tells you who is due a follow-up today, and shows how far applications
get, broken down by where they came from.

The problem it solves: a job search run from a spreadsheet loses two things. Follow-ups slip, because
nothing says "this one has been quiet for a week". And there is no honest answer to "which channel
works", because a spreadsheet keeps only the current status, not the path an application took.

**Goals**

- Track applications through a fixed set of statuses, with every status change recorded.
- Set and clear follow-up dates automatically, so the follow-up list is always right.
- Show funnel numbers: how many applications sit in each status, and the applied-to-screen rate per
  source.

**Non-goals**

- Login, multiple users, sharing.
- Email or calendar integration, reminders, notifications.
- Importing from spreadsheets or job boards.
- Drag and drop, a kanban board.

## Users and stories

One persona: a person in an active job search with 20–100 applications open at once.

| ID | As a user, I want to… | So that… |
| --- | --- | --- |
| US-1 | add an application with company, role, link and source | I have one place for every application |
| US-2 | change an application's status and add a note | the record shows what happened and when |
| US-3 | see the history of status changes on an application | I can tell how long each step took |
| US-4 | see a list of applications due a follow-up today or earlier | nothing goes quiet without me noticing |
| US-5 | see counts per status and the applied-to-screen rate per source | I know which channel is worth my time |
| US-6 | filter the list by status | I can focus on one stage at a time |

## Functional requirements

| ID | Area | Requirement |
| --- | --- | --- |
| FR-1 | Applications | Create, read, edit, delete and list applications. Delete removes the application's events too. |
| FR-2 | Applications | The list is filterable by one status and ordered by `updated_at`, newest first. |
| FR-3 | Status | Status changes only through `POST /applications/{id}/status`. `PATCH` cannot change status. |
| FR-4 | History | Creating an application and every status change write an event: from, to, when, optional note. |
| FR-5 | Dates | Moving to `applied` sets `applied_date` to today if it is empty, and `follow_up_date` to today + 7 days. |
| FR-6 | Dates | Moving to `offer`, `rejected` or `ghosted` clears `follow_up_date`. |
| FR-7 | Follow-ups | Lists applications whose `follow_up_date` is today or earlier and whose status is `applied`, `screen` or `interview`. |
| FR-8 | Funnel | Counts per status, and per source: applications that reached `applied`, those that reached `screen`, and the rate between them. |
| FR-9 | UI | Pages: list with status filter, create/edit form, detail with history and status change, follow-ups, funnel. |
| FR-10 | Ops | `/health` (process is up) and `/ready` (database answers). JSON logs with a request id. |

"Today" is the server's current date in UTC.

## Data model

**applications**

| Column | Type | Rules |
| --- | --- | --- |
| id | UUID | primary key, generated by the server |
| company | string | required, 1–100 chars after trimming |
| role | string | required, 1–100 chars after trimming |
| link | string, nullable | up to 500 chars; when present must start with `http://` or `https://` |
| source | enum | `cold`, `inbound`, `referral`; required |
| status | enum | `saved`, `applied`, `screen`, `interview`, `offer`, `rejected`, `ghosted`; `saved` on create |
| applied_date | date, nullable | set by FR-5, editable through `PATCH` |
| follow_up_date | date, nullable | set and cleared by FR-5 and FR-6, editable through `PATCH` |
| notes | text, nullable | up to 5,000 chars |
| created_at, updated_at | timestamp with time zone | set by the server; `updated_at` changes on every edit and status change |

**status_events**

| Column | Type | Rules |
| --- | --- | --- |
| id | UUID | primary key |
| application_id | UUID | foreign key, `ON DELETE CASCADE` |
| from_status | enum, nullable | `null` for the event written on create |
| to_status | enum | |
| note | string, nullable | up to 500 chars |
| created_at | timestamp with time zone | |

Index on `status_events(application_id, created_at)`.

## Business rules

**Statuses.** Any status may move to any other status; real searches go backwards (a "ghosted" company
writes back). Moving to the status the application already has is rejected with `409
invalid_transition`.

**Dates on a status change** (applied in the same transaction as the event):

| Moving to | `applied_date` | `follow_up_date` |
| --- | --- | --- |
| `applied` | set to today if empty, otherwise kept | today + 7 days |
| `offer`, `rejected`, `ghosted` | kept | cleared |
| `saved`, `screen`, `interview` | kept | kept |

**Reached a stage.** An application *reached applied* if any of its events has `to_status` in
`applied`, `screen`, `interview`, `offer`. It *reached screen* if any event has `to_status` in `screen`,
`interview`, `offer`. Rejected and ghosted are outcomes, not stages, so they count only through the
stages before them.

**Funnel.** `by_status`: the current count for every status, zeros included. `by_source`: one row per
source, always all three, with `applied` (reached applied), `reached_screen`, and `screen_rate =
reached_screen / applied` rounded to 3 decimals, or `null` when `applied` is 0.

**Follow-ups** are ordered by `follow_up_date` ascending, then company.

## API

All endpoints are under `/api/v1`; `openapi.yaml` at the repo root is the contract and is written
before the code. JSON uses `snake_case`; dates are `YYYY-MM-DD`; timestamps are ISO 8601 in UTC.

| Method | Path | Does | Success |
| --- | --- | --- | --- |
| GET | `/applications?status=` | list, optionally filtered by one status | 200 |
| POST | `/applications` | create; `status` is not accepted, starts at `saved` | 201 |
| GET | `/applications/{id}` | one application | 200 |
| PATCH | `/applications/{id}` | partial edit of company, role, link, source, applied_date, follow_up_date, notes | 200 |
| DELETE | `/applications/{id}` | delete with its events | 204 |
| POST | `/applications/{id}/status` | body `{"status", "note"?}`; applies the rules, returns the application | 200 |
| GET | `/applications/{id}/events` | the history, oldest first | 200 |
| GET | `/followups` | applications due a follow-up (FR-7) | 200 |
| GET | `/stats/funnel` | `{"total", "by_status": {...}, "by_source": [...]}` | 200 |

Outside the prefix: `GET /health` returns `{"status": "ok", "version"}`; `GET /ready` returns 200
when a `SELECT 1` succeeds and 503 otherwise.

**Errors.** Every non-2xx response is `{"error": {"code", "message", "details"}}`.

| Code | Status | When |
| --- | --- | --- |
| `validation_error` | 422 | bad body or query: missing field, wrong type, length, unknown field, bad enum |
| `not_found` | 404 | no application with that id, or a malformed id |
| `invalid_transition` | 409 | moving to the current status |
| `internal_error` | 500 | anything unexpected; details never include a stack trace |

## Frontend

React + TypeScript + Vite, no UI framework. Components never call `fetch`; everything goes through the
typed client in `frontend/src/api/`. Hash routing, five views:

1. **Applications**: table with company, role, source, status, applied date, follow-up date; a status
   filter; a "New application" button. Rows open the detail.
2. **Form**: create and edit; shows the server's validation message next to the form.
3. **Detail**: all fields, a status selector with an optional note, the history list, edit and delete.
4. **Follow-ups**: the FR-7 list, overdue dates highlighted.
5. **Funnel**: a count per status and a per-source table with the rate as a percentage.

## Stack and operations

- **Backend:** Python 3.14, FastAPI, Pydantic v2, SQLAlchemy 2.0, Alembic, uv. Layers `api/` →
  `services/` → `repositories/`.
- **Database:** PostgreSQL 16 in Compose and production. SQLite for the fast API tests.
- **Frontend:** React 19, TypeScript, Vite, vitest.
- **Container:** one multi-stage `Dockerfile`: build the frontend, then a Python image serves the API
  and the built frontend. Migrations run on start.
- **Config:** environment variables only — `DATABASE_URL`, `LOG_LEVEL`, `SEED_DEMO_DATA`,
  `APP_VERSION`, `OTEL_EXPORTER_OTLP_ENDPOINT`. `.env.example` documents them.
- **Seed data:** with `SEED_DEMO_DATA=true` and an empty database, the app creates about ten invented
  applications at start (made-up companies, no real people) so a fresh deployment has something to show.
- **Logs:** one JSON object per line. Each request logs method, path, status, duration and a request id
  (taken from `X-Request-ID` or generated, and returned in that header). No request bodies, no
  application fields in logs.
- **Telemetry (#29):** with `OTEL_EXPORTER_OTLP_ENDPOINT` set, OpenTelemetry traces, metrics and the
  same JSON log lines (with `trace_id`, `span_id`) go to an OTLP collector; unset, telemetry is off.
  Local only: the Compose `observability` profile (Collector, Prometheus, Tempo, Loki, Grafana). No
  application fields or credentials in any signal.
- **Tests:** unit tests for the rules and the funnel maths, API tests on SQLite, integration tests on
  PostgreSQL. `make test` runs all of them and the frontend tests.
